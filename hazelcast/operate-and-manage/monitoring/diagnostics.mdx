Hazelcast diagnostic logging helps you troubleshoot and monitor a cluster.

Members and clients both provide a set of diagnostics plugins. Hazelcast writes the diagnostics to a dedicated log file.

You can configure diagnostic logging in two ways:
- Dynamic configuration: use Management Center or Operator, without restarting the cluster
- Static configuration: set the properties described on this page

## Enable dynamic logging

With dynamic diagnostic logging, you can turn diagnostic logging on and off at runtime without restarting the cluster.

You can also turn diagnostic logging off automatically after a set period by configuring the auto turn-off feature in Management Center or Operator.

In Operator, you can also control the diagnostic plugins.

To learn how to enable dynamic diagnostic logging and the auto turn-off feature, see the <Variable href="/operator/{page-latest-supported-po}/configure-diagnostic-logging" text="Operator"/> or <Variable href="/management-center/{page-latest-supported-mc}/clusters/diagnostic-logging" text="Management Center" /> documentation.

:::important

A diagnostics property that you set statically overrides the dynamic configuration of the same setting. For example, if you set the `hazelcast.diagnostics.enabled` property to `true`, you cannot disable diagnostics dynamically in Management Center or Operator. If you set it to `false`, you cannot enable diagnostics dynamically. To control a setting dynamically, do not set its property statically.

:::

## Enable static logging

To enable diagnostic logging statically, set the following properties on the members:

<Tabs groupId="java--jvm--xml--yaml">
<TabItem value="xml" label="XML">

```xml
<hazelcast>
    ...
    <properties>
        <property name="hazelcast.diagnostics.enabled">true</property>
        <property name="hazelcast.diagnostics.invocation.sample.period.seconds">30</property>
        <property name="hazelcast.diagnostics.pending.invocations.period.seconds">30</property>
        <property name="hazelcast.diagnostics.slowoperations.period.seconds">30</property>
        <property name="hazelcast.diagnostics.storeLatency.period.seconds">60</property>
    </properties>
    ...
</hazelcast>
```

</TabItem>
<TabItem value="yaml" label="YAML">

```yaml
hazelcast:
    ...
    properties:
      hazelcast.diagnostics.enabled: true
      hazelcast.diagnostics.invocation.sample.period.seconds: 30
      hazelcast.diagnostics.pending.invocations.period.seconds: 30
      hazelcast.diagnostics.slowoperations.period.seconds: 30
      hazelcast.diagnostics.storeLatency.period.seconds: 60
    ...
```

</TabItem>
<TabItem value="java" label="Java">

```java
Config config = new Config();
config.setProperty( "hazelcast.diagnostics.enabled", "true" )
      .setProperty( "hazelcast.diagnostics.invocation.sample.period.seconds", "30" )
      .setProperty( "hazelcast.diagnostics.pending.invocations.period.seconds", "30" )
      .setProperty( "hazelcast.diagnostics.slowoperations.period.seconds", "30" )
      .setProperty( "hazelcast.diagnostics.storeLatency.period.seconds", "60" );
```

</TabItem>

```shell title="JAVA_OPTS"

```

</TabItem>

On a Java client, set the following property:
- `hazelcast.diagnostics.enabled=true`


</TabItem>

```java

```

</TabItem>
<TabItem value="jvm" label="JVM">

```shell title="Java command"

```

```shell title="JAVA_OPTS"
JAVA_OPTS="-Dhazelcast.diagnostics.stdout=STDOUT"
```

The property accepts the following types:
- `FILE` outputs to a [set of files](#configure-the-diagnostics-log-file) managed by Hazelcast. This is the default type.
- `STDOUT` outputs to the standard output.
- `LOGGER`outputs to the Hazelcast logger. You can then forward the diagnostics to any output that the logging framework supports.

  :::note

  The `LOGGER` type uses more CPU and memory than the other output types, because each diagnostics write passes through the logging framework. It also gives you more flexibility.

  :::

### Send diagnostics to a logging framework

Hazelcast does not require a specific logging framework. To forward the diagnostics to your logging framework, set the `hazelcast.diagnostics.stdout` property to `LOGGER`:

```xml
    ...
    <properties>
        <property name="hazelcast.diagnostics.stdout">LOGGER</property>
    </properties>
    ...
</hazelcast>
```

</TabItem>
<TabItem value="yaml" label="YAML">

```yaml

    ...

      hazelcast.diagnostics.stdout: LOGGER
    ...
```

</TabItem>

```java

```

</TabItem>
<TabItem value="jvm" label="JVM">

```shell title="Java command"

```

```shell title="JAVA_OPTS"
JAVA_OPTS="-Dhazelcast.diagnostics.stdout=LOGGER"
```

</TabItem>

This configuration forwards the logs to the `com.hazelcast.diagnostics` logger. To write them to a file, reference one of your configured appenders from that logger. The following example does this for Log4j2:

```xml
<Logger name="com.hazelcast.diagnostics" level="debug" additivity="false">
    <AppenderRef ref="LogToRollingFile"/>
</Logger>
```

To control the file size and rolling behavior, configure [`TimeBasedTriggeringPolicy`](https://logging.apache.org/log4j/2.x/manual/configuration.html) and [`SizeBasedTriggeringPolicy`](https://logging.apache.org/log4j/2.x/manual/configuration.html) for the appender.

:::note

The diagnostic logs have the `DEBUG` level by default. If the root appender uses the `DEBUG` level and you do not want the diagnostic logs in the member logs, set the level of the `com.hazelcast.diagnostics` logger to `INFO`. For Log4j2, see the [configuration documentation](https://logging.apache.org/log4j/2.x/manual/configuration.html).

:::

## Diagnostics plugins

Diagnostics consists of plugins, such as `BuildInfo`, `SystemProperties`, and `HazelcastInstance`.

### `BuildInfo`

The `BuildInfo` plugin shows Hazelcast build information, including the release number, the Git revision number, and whether you have Hazelcast <Variable name="enterprise-product-name" />.

### `SystemProperties`

The `SystemProperties` plugin shows the system properties that are used by and configured for your Hazelcast installation, with their values. These are the properties whose names start with `java` (except `java.awt`), `hazelcast`, `sun`, and `os`. The plugin also shows the arguments used to start the JVM.

### `ConfigProperties`

The `ConfigProperties` plugin shows the Hazelcast properties that you set explicitly in the declarative or programmatic configuration, with their values. It does not show properties set only on the command line with `-D`.

### `Metrics` {/* #diagnostics-metrics */}

The Metrics plugin writes a comprehensive log of what is happening in your Hazelcast system. See [Metrics](./metrics.mdx) for more information.

To set how often the plugin writes to the log file, use the following property:
- `hazelcast.diagnostics.metrics.period.seconds`: Set a value in seconds. Its default value is `60` seconds.

:::note

See the [List of Hazelcast Metrics appendix](../../reference/list-of-metrics.mdx) for the full list of metrics with their descriptions.

:::

### `SlowOperations`

The `SlowOperations` plugin shows slow operations and invocations. See the [`SlowOperationDetector` section](../../develop-and-build/best-practices/threading.mdx#slowoperationdetector) for more information.

### `Invocations`

The Invocations plugin shows statistics about current and past invocations, including pending invocations, the history of invocations, and the slow history. The slow history holds every sample where an invocation took longer than the threshold. It includes the invocations whose operations took a long time, and any other invocations that were obstructed.

To set how often the plugin scans all pending invocations, and the threshold above which an invocation counts as slow, use the following properties:
- `hazelcast.diagnostics.invocation.sample.period.seconds`: Set a value in seconds. Its default value is `0`, which disables the plugin.
- `hazelcast.diagnostics.invocation.slow.threshold.seconds`: Set a value in seconds. Its default value is `5` seconds.

### `InvocationProfiler`

The `InvocationProfiler` plugin shows invocation latencies for each operation. The following example shows its output:

```none

                                          64..127us=346

                          com.hazelcast.map.impl.operation.GetOperation[
                                  count=100

                                  avg(us)=190
                                  max(us)=1,000
                                  latency-distribution[
                                          64..127us=81

```

To set how often the plugin scans all invocations, use the following system property:
- `hazelcast.diagnostics.invocation-profiler.period.seconds`: Set a value in seconds. Its default value is `5` seconds. You can set it to `0` to disable the plugin.

To reduce the number of log entries, increase this period.

### `OperationProfiler`

The `OperationProfiler` plugin measures how long each operation runs on an operation thread. For a blocking or offloaded operation, it measures only the time on the operation thread. The following example shows its output:

```none

                                  count=502,501
                                  totalTime(us)=1,690,645

                                  max(us)=462

                                          2..4us=359,876

```

To set how often the plugin scans all operations, use the following system property:
- `hazelcast.diagnostics.operation-profiler.period.seconds`: Set a value in seconds. Its default value is `5` seconds. You can set it to `0` to disable the plugin.

### `HazelcastInstance`

The `HazelcastInstance` plugin shows the basic state of your cluster, including the number and addresses of the current members and the address of the oldest member. Use it to see the state of the cluster without analyzing a lot of data.

To set how often the plugin writes the cluster information to the log file, use the following property:
- `hazelcast.diagnostics.memberinfo.period.seconds`: Set a value in seconds. Its default value is `60` seconds.

### `EventQueue`

The `EventQueue` plugin checks the event queues of data structures, and samples the event types when a queue holds more events than a threshold. Use it to find out why an event queue is filling up.

To configure the plugin, use the following properties:
- `hazelcast.diagnostics.event.queue.period.seconds`: Interval, in seconds, between the runs in which this plugin gathers information and writes it to the diagnostics log file. The default value `0` disables the plugin.
- `hazelcast.diagnostics.event.queue.threshold`: Minimum number of events in the queue before the plugin samples it. Its default value is `1000`.
- `hazelcast.diagnostics.event.queue.samples`: Number of samples to take from the event queue. More samples give a more accurate result, but reduce performance. Its default value is `100`.

The following example shows the output for a map:

```none
17-04-2019 17:36:37 EventQueues[
    worker=1[
        eventCount=441
        sampleCount=100
        samples[
            IMap 'myMap' ADDED sampleCount=51 51.000%
            IMap 'myMap' REMOVED sampleCount=49 49.000%]]
```

### `SystemLog`

The `SystemLog` plugin shows the activity in your cluster, such as connections and members being added or removed, and changes in the lifecycle of the cluster. It also shows why connections were closed.

To enable or disable the plugin, and to set whether it shows information about partition migrations, use the following properties:
- `hazelcast.diagnostics.systemlog.enabled`: Whether the plugin is enabled. Its default value is `true`.
- `hazelcast.diagnostics.systemlog.partitions`: Whether the plugin shows information about partition migrations. Its default value is `false`. If you enable it on a cluster with many partitions, the plugin can write a large number of log entries.

### `StoreLatency`

The `StoreLatency` plugin shows statistics for each store. The statistics include the call count, the average and maximum latency, and the latency distribution of each store method, such as `load`, `loadAll`, and `loadAllKeys`.

:::note

You cannot enable the `StoreLatency` plugin dynamically.

:::

The following example shows the output in the diagnostics log file for a `MapStore`:

```none
17-9-2019 13:12:34 MapStoreLatency[
    map[
        loadAllKeys[
            count=1
            totalTime(us)=8
            avg(us)=8
            max(us)=8
            latency-distribution[
                0..99us=1]]
        load[
            count=100
            totalTime(us)=4,632,190
            avg(us)=46,321
            max(us)=99,178
            latency-distribution[
                0..99us=1
                1600..3199us=3
                3200..6399us=3
                6400..12799us=7
                12800..25599us=13
                25600..51199us=32
                51200..102399us=41]]]]
```

The plugin writes similar output for JCache, `Queue`, and `Ringbuffer` data structures that use persistent data stores.

To configure the `StoreLatency` plugin, use the following properties:
- `hazelcast.diagnostics.storeLatency.period.seconds`: Interval, in seconds, at which this plugin writes the collected information to disk. The plugin is disabled by default. A sensible production value is `60` seconds.
- `hazelcast.diagnostics.storeLatency.reset.period.seconds`: Interval, in seconds, at which the plugin resets the statistics. For example, with a value of `300`, the plugin clears all statistics every 5 minutes. Its default value is `0`, which means the plugin does not reset the statistics.

### `OperationHeartbeats`

The `OperationHeartbeats` plugin shows the deviation in operation heartbeats between members. Each member sends an operation heartbeat to every other member, whether or not an operation is running on behalf of that member. The heartbeat contains a list of the `callId` values of all running operations from a given member. This plugin also works between members and lite members.

Members send operation heartbeats at an interval of a quarter of the operation call timeout. With the default call timeout of 60 seconds, a member expects an operation heartbeat every 15 seconds. Operation heartbeats are high-priority packets, which overtake regular packets. A separate thread in the invocation monitor processes them. If the interval between these packets deviates, the cause can be a problem such as network latency.

The following example shows the output when a member has not received an operation heartbeat for 37 seconds:

```none
20-07-2017 11:12:55 OperationHeartbeat[
    member[10.212.1.119]:5701[
        deviation(%)=146.6666717529297
        noHeartbeat(ms)=37,000
        lastHeartbeat(ms)=1,500,538,338,603
        lastHeartbeat(date-time)=20-07-2017 11:12:18
        now(ms)=1,500,538,375,603
        now(date-time)=20-07-2017 11:12:55]]
```

The `OperationHeartbeats` plugin is enabled by default because it has little overhead and only prints to the diagnostics file if the maximum deviation percentage (explained below) is exceeded.

To configure the `OperationHeartbeats` plugin, use the following properties:
- `hazelcast.diagnostics.operation-heartbeat.seconds`: Interval, in seconds, at which this plugin writes the collected information to disk. Its default value is `10`. A value of `0` disables the plugin.
- `hazelcast.diagnostics.operation-heartbeat.max-deviation-percentage`: The maximum allowed deviation percentage. Its default value is `33`. For example, with the default call timeout of 60 seconds, the operation heartbeat interval is 15 seconds. A deviation percentage of 33 allows a maximum deviation of 5 seconds. A packet that arrives after 19 seconds is within the limit. If a packet arrives after 21 seconds, the plugin writes to the diagnostics file.

### `MemberHeartbeats`

The `MemberHeartbeats` plugin is similar to the `OperationHeartbeats` plugin, but it measures the deviation in cluster heartbeats between members instead of operation heartbeats. Every member sends a heartbeat to the other members every 5 seconds by default.

Like the `OperationHeartbeats` plugin, the `MemberHeartbeats` plugin can detect networking problems long before they lead to problems such as split-brain syndrome.

The following example shows the output when a member has not received a heartbeat from another member for 11 seconds:

```none
20-07-2017 19:32:22 MemberHeartbeats[
    member[10.212.1.119]:5701[
        deviation(%)=120.0
        noHeartbeat(ms)=11,000
        lastHeartbeat(ms)=1,500,568,331,645
        lastHeartbeat(date-time)=20-07-2017 19:32:11
        now(ms)=1,500,568,342,645
        now(date-time)=20-07-2017 19:32:22]]
```

The `MemberHeartbeats` plugin is enabled by default because it has little overhead and only prints to the diagnostics file if the maximum deviation percentage (explained below) is exceeded.

To configure the `MemberHeartbeats` plugin, use the following properties:
- `hazelcast.diagnostics.member-heartbeat.period.seconds`: Interval, in seconds, at which this plugin writes the collected information to disk. Its default value is `10`. A value of `0` disables the plugin.
- `hazelcast.diagnostics.member-heartbeat.max-deviation-percentage`: The maximum allowed deviation percentage. Its default value is `100`. For example, if members send heartbeats every 5 seconds, a 100% deviation allows heartbeats to arrive up to 5 seconds after they are expected. The plugin does not write a heartbeat that arrives after 9 seconds, but writes one that arrives after 11 seconds.

### `OperationThreadSamples`

The `OperationThreadSamples` plugin samples the operation threads and checks the running operations and tasks. The Hazelcast [slow operation detector](../../develop-and-build/best-practices/threading.mdx#slowoperationdetector) is useful for slow operations, but it can be inefficient for a high volume of operations that are only slightly slow. The `OperationThreadSamples` plugin shows more clearly which operations are running.

To configure the `OperationThreadSamples` plugin, use the following properties:
- `hazelcast.diagnostics.operationthreadsamples.period.seconds`: Interval, in seconds, at which this plugin writes the collected information to disk. An efficient value for production is 30 seconds or more. The default value `0` disables the plugin.
- `hazelcast.diagnostics.operationthreadsamples.sampler.period.millis`: Interval, in milliseconds, between samples. A lower value increases both the overhead and the precision. Its default value is `100`.
- `hazelcast.diagnostics.operationthreadsamples.includeName`: Whether to include the name of the data structure that the operation targets, if available, in the name of each sample. Its default value is `false`.

The following example shows the output when the `hazelcast.diagnostics.operationthreadsamples.includeName` property is `false`:

```none
28-08-2019 07:40:07 1535442007330 OperationThreadSamples[
    Partition[
        com.hazelcast.map.impl.operation.MapSizeOperation=304623 85.6927%
        com.hazelcast.map.impl.operation.PutOperation=33061 9.300304%
        com.hazelcast.map.impl.operation.GetOperation=17799 5.0069904%]
    Generic[
        com.hazelcast.internal.nio.Packet=1767 27.361412%
        com.hazelcast.internal.cluster.impl.operations.JoinRequestOp=821 12.712914%
        com.hazelcast.spi.impl.operationservice.impl.operations.PartitionIteratingOperation=278 4.3047385%
        com.hazelcast.internal.cluster.impl.operations.HeartbeatOp=93 1.4400743%
        com.hazelcast.internal.cluster.impl.operations.OnJoinOp=89 1.3781357%
        com.hazelcast.internal.cluster.impl.operations.WhoisMasterOp=75 1.1613503%]]
```

In this example, `MapSizeOperation` operations run on the operation threads most of the time.

```none
                                                  updateCount=1,000
```
