The CP Subsystem requires manual intervention while expanding or shrinking its size, or when a CP member crashes or becomes unreachable. When a CP member becomes unreachable, it is not immediately removed from the CP Subsystem because it could still be active behind a partition. By default, missing CP members are automatically removed after four hours and are replaced by other CP members if any are available.

## Tools

You can manage and monitor the CP Subsystem using the following tools:

- <Variable href="/management-center/{page-latest-supported-mc}/cp-subsystem/dashboard" text="Management Center" />
- <Variable href="https://docs.hazelcast.org/docs/{os-version}/javadoc/com/hazelcast/cp/CPSubsystemManagementService.html" text="Java member API" />
- [Community Edition REST API](../../clients-and-apis/apis/enterprise-rest-api/rest-api.mdx)

  - REST endpoint URL
  - `hz-cluster-cp-admin` shell script, which comes with the Hazelcast package (requires `curl`).

    :::caution[Deprecation Notice for the Community Edition REST API]

    The Community Edition REST API is deprecated and is scheduled for removal in Hazelcast version 7.0. An improved Enterprise version of this feature is available and actively being developed. For more information, see [Enterprise REST API](../../clients-and-apis/apis/enterprise-rest-api/overview.mdx).

    :::

  The REST API and its `CP` endpoint group are disabled by default. Before you use the REST examples on this page, [enable the REST API](../../clients-and-apis/apis/enterprise-rest-api/rest-api.mdx#enabling-rest-api) and the [`CP` endpoint group](../../clients-and-apis/apis/enterprise-rest-api/rest-api.mdx#using-rest-endpoint-groups).

### Promote a local member to a CP member

You can add a CP member to increase the number of CP members available for new CP groups, or to fill missing slots in existing CP groups. After the initial Hazelcast cluster startup, you can promote any existing member that is not a [lite member](../maintaining-a-cluster/lite-members.mdx) to the CP member role.

The new CP member automatically joins CP groups that have missing members, and the majority values of these CP groups are recalculated. A group is missing members when its current size is smaller than the configured [`group-size`](./configuration.mdx#group-size). A member with [`auto-step-down-when-leader`](./configuration.mdx#auto-step-down-when-leader) enabled does not join a group that would then have too few members that can become leader.

If the local member is already a CP member, promoting it has no effect.

:::note

When a member is promoted to a CP member, it generates an additional UUID that other CP members can use to identify it. See [CP members](./cp-subsystem.mdx#cp-members).

:::

### Remove a CP member

You can remove a specified CP member from the active CP members list and all CP groups it belongs to. If any other active CP member is available, it replaces the removed CP member in its CP groups. Otherwise, the affected CP groups shrink and their majority values are recalculated. A CP member with [`auto-step-down-when-leader`](./configuration.mdx#auto-step-down-when-leader) enabled is not used as a replacement if the group would then have too few members that can become leader.

:::warning

Before removing a CP member from the CP Subsystem, make sure that it is declared as unreachable by the [failure detector](../fault-tolerance/detecting-failures/failure-detector-configuration.mdx) and removed from the member list. The behavior is undefined when a running CP member is removed from the CP Subsystem.

:::

### Shut down CP members

CP member shutdown behavior varies depending on whether CP Subsystem Persistence is enabled or not.

#### Persistence disabled

CP Subsystem Persistence is disabled by default. Without Persistence, CP members keep their state only in memory, and a CP member that shuts down cannot rejoin with its CP identity and state. Therefore, a shutting down CP member is removed from the CP Subsystem and replaced with other available CP members in all of its CP groups. This avoids decreasing group size or losing majorities.

A CP member with [`auto-step-down-when-leader`](./configuration.mdx#auto-step-down-when-leader) enabled is not used as a replacement if the group would then have too few members that can become leader. If no CP member can replace a shutting down CP member in a CP group, the group shrinks by one and its majority value is recalculated.

When CP Subsystem Persistence is disabled, if there are `N` CP members in the CP Subsystem, you can shut down `N-2` CP members concurrently. Once these `N-2` CP members complete their shutdown, the remaining CP members must be shut down one at a time. Even though the shutdown API can be called concurrently on multiple members, the `METADATA` CP group handles shutdown requests serially. Therefore, it is simpler to shut down CP members one by one by calling `HazelcastInstance.shutdown()` on the next CP member once the current CP member completes its shutdown.

:::note

The reasoning behind this behavior is as follows. Each shutdown request internally requires a Raft commit to the `METADATA` CP group when CP Subsystem Persistence is disabled. A CP member proceeds to shutdown after it receives a response to this commit.

To be able to perform a Raft commit, the `METADATA` CP group must have its majority up and running. When only two CP members are left after graceful shutdowns, the majority of the `METADATA` CP group becomes two. If the last two CP members shut down concurrently, one of them is likely to perform its Raft commit faster and leave the cluster. The other CP member has not yet completed its Raft commit.

In this case, the last CP member waits for a response to its commit attempt on the `METADATA` CP group, and eventually times out. This causes an unnecessary delay in the shutdown of the last CP member.

Suppose the last two CP members shut down serially instead. The `N-1`th member then receives the response to its commit after its shutdown request is also committed on the last CP member. The last CP member then finds from its local data that it is the last CP member alive. It shuts down without attempting a Raft commit on the `METADATA` CP group.

:::

#### Persistence enabled

When CP Subsystem Persistence is enabled, a shut-down CP member can come back by restoring its CP state. Therefore, it is not automatically removed from the CP Subsystem. It is up to you to remove shut-down CP members via `CPSubsystemManagementService.removeCPMember(UUID)` if they do not come back. Shutting down CP members are still kept in the CP Subsystem and are part of the CP group majority calculations. You can shut down any number of CP members at the same time.

See [CP Membership Listeners](#cp-membership-listeners) to get notified about the CP member additions and removals. See also [Shutting Down a Hazelcast Member](../maintaining-a-cluster/shutdown.mdx#shutting-down-a-hazelcast-member) for general information on shutting down specific members and considerations to take into account.

## CP groups

Use the following operations to create and view CP groups.

### Create CP groups

To create a custom CP group, add `@` and the group name to the end of the data structure's name. The data structure is stored in that group, and the group is created if it does not exist. For example, `.getAtomicLong("myAtomicLong@myGroup")` creates a CP group called `myGroup` and initializes an atomic long called `myAtomicLong` in it.

For most use cases, the `default` CP group should be sufficient to maintain all CP data structure instances. See [CP Subsystem best practices](./best-practices.mdx).

### CP group availability listeners

`CPGroupAvailabilityListener` is notified when the availability of a CP group decreases or it loses the majority completely.

In general, the availability decreases when a CP member becomes unreachable because of a process crash, network partition, out-of-memory error, or graceful shutdown. Once a member is declared unavailable by the failure detector, that member is removed from the cluster. If it is also a CP member, a `CPGroupAvailabilityEvent` is fired for each CP group that member belongs to.

`CPGroupAvailabilityListener` has a separate method to report the loss of majority.

The listener interface has methods that are invoked for the following events:

- `availabilityDecreased`: a CP group's availability decreases, but the group still has the majority of its members available.

## Recover from a lost majority {/* #handle-a-lost-majority */}

When the majority of a CP group is lost, that CP group cannot make further progress. New CP members cannot join a CP group that has lost majority because membership changes must also go through the Raft consensus algorithm.

- If the group is not the `METADATA` CP group, you must [force-destroy](#destroy-a-cp-group-by-force) the group immediately because it can block the `METADATA` CP group from performing membership changes on the CP Subsystem.
- If the majority of the `METADATA` CP group permanently crashes, it is equivalent to the permanent crash of the whole CP Subsystem, even if other CP groups are running fine. In this case, you must [reset the CP Subsystem](#wipe-and-reset-the-cp-subsystem).

### Destroy a CP group by force

You can force-destroy any active CP group other than the `METADATA` CP group. A force-destroy does not use the Raft algorithm. Use it only when a CP group loses its majority and cannot make progress anymore.

Membership changes in CP groups, such as CP member promotion or removal, are usually done via the Raft consensus algorithm. However, a CP group that permanently loses its majority cannot commit any new operations. A force-destroy ungracefully stops the Raft algorithm for the CP group on its remaining members. The members themselves keep running. The force-destroy also performs a Raft commit to the `METADATA` CP group to update the status of the destroyed group.

Once a CP group is destroyed, all CP data structure proxies created before the destroy fail with `CPGroupDestroyedException`. However, if a new proxy is created afterward, this CP group is re-created from scratch with a new set of CP members.

A force-destroy is idempotent. It has no effect if the CP group is already destroyed.

### Wipe and reset the CP Subsystem

You must wipe and reset the whole CP Subsystem state only when the `METADATA` CP group loses its majority and cannot make progress anymore.

After a reset, all CP state and data is wiped, including data written by CP Subsystem Persistence, and CP members start with no state.

You can start a reset only from the Hazelcast master member, which is the first member in the Hazelcast cluster member list. Moreover, the Hazelcast cluster must have at least the number of members configured in the [`cp-member-count`](./configuration.mdx#cp-member-count) option.

Do not reset the CP Subsystem while there are membership changes in the Hazelcast cluster. Before you reset, make sure that there is no new member joining and all existing Hazelcast members have seen the same member list.

A reset triggers a new CP discovery round. If the new CP discovery round fails for any reason, Hazelcast members are not terminated. Hazelcast members are likely to contain data for AP data structures, and terminating them can cause data loss. Therefore, observe the cluster and check whether the CP discovery process completes successfully.

:::warning

A reset is **not** idempotent, and multiple resets can break the whole system. After you start a reset, observe the system to see whether the reset completes or fails before you try again.

:::

All CP groups that existed before the reset are destroyed; new groups are created on demand as proxies request them. CP proxies obtained before the reset remain bound to the destroyed groups. Operations on them fail, typically with `CPGroupDestroyedException`.

Proxies are not rebound to the new groups automatically. A new CP group shares no history with the group it replaces, and silently redirecting operations to it would break the linearizable history the CP Subsystem guarantees. This differs from AP data structures.

After the reset completes successfully, discard the CP proxies you are holding and obtain new ones. Members and clients do not need to be restarted.

:::warning

Mutual exclusion does not hold across a reset. All CP sessions are wiped. Locks held and permits acquired before the reset cease to exist, and the holder is not notified. The holder finds out only when it next calls into the proxy and receives `IllegalMonitorStateException`. Another caller can acquire the same lock in the new group in the meantime.

:::
