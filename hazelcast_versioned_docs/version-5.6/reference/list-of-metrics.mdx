The tables below list Hazelcast metrics and descriptions, grouped by subject. This page includes both member-side and client-side metrics.

Unless noted otherwise, metrics are member-side and local to the instance that reports them. For members, distributed data structure metrics reflect the local statistics for the partition data held on that member.

Some metrics represent cluster-wide agreed values obtained by communicating with other members in the cluster. In those cases, each value still reflects the local member's current view of the cluster (for example, in split-brain scenarios). The `clusterStartTime` metric is one example; on a local member, its value is obtained from the master member.

Metric names on this page are canonical names. Some metrics are exposed with different prefixes depending on where they are collected (member, client, or subsystem). Sections that have prefix variants call them out explicitly.

:::note

If you use Management Center to export cluster-wide metrics to Prometheus, Management Center reformats the metrics to align with Prometheus best practice recommendations. See <Variable href="/management-center/{page-latest-supported-mc}/integrate/prometheus-monitoring" text="Prometheus Monitoring" />.

:::

## Streaming engine cluster-wide metrics

Each member reports one value for each metric:

| Name | Description | Tags |
| --- | --- | --- |
| `blockingWorkerCount` | Number of non-cooperative workers employed | None |
| `jobs.submitted` | Number of computational jobs submitted | None |
| `jobs.completedSuccessfully` | Number of computational jobs successfully completed | None |
| `jobs.completedWithFailure` | Number of computational jobs that have failed | None |
| `jobs.executionStarted` | Number of computational job executions started | None |
| `jobs.executionTerminated` | Number of computational job executions finished | None |
| `jobs.executionCompleted` | Number of computational job executions completed successfully or otherwise | None |

A job can execute more than once, for example when it is restarted, or suspended and then resumed. The `jobs.execution*` metrics count each execution.

Each member reports one value for each metric for each of its cooperative worker threads:

| Name | Description | Tags |
| --- | --- | --- |
| `iterationCount` | Total number of iterations that the tasklet driver in the cooperative worker thread has made | `cooperativeWorker` |
| `taskletCount` | Number of tasklets assigned to the cooperative worker thread | `cooperativeWorker` |

The `iterationCount` value should increase by at least 250 iterations per second. A lower rate means that some cooperative processors block for too long, which increases latency. A somewhat lower rate is normal when many tasklets are assigned to the processor.

## Streaming engine job-specific metrics {/* #job-metrics */}

All job-specific metrics have the `job` tag, which holds the name and ID of the job, and the `exec` tag, which holds the job execution ID. Most of them also have the `vertex` tag, which holds the vertex name. As a result, most of these metrics have at least one instance for each vertex of each current job execution.

Additionally, if the vertex sourcing them is a data source or data sink, then the `source` or `sink` tags will also be set to true.

Each member reports one value for each metric for each job execution:

| Name | Description | Tags |
| --- | --- | --- |
| `executionStartTime` | Start time of the current execution of the job, as epoch time in milliseconds | `job`, `exec` |
| `executionCompletionTime` | Completion time of the current execution of the job, as epoch time in milliseconds | `job`, `exec` |
| `status` | Status of the job, as a number | `job`, `exec` |
| `userCancelled` | Whether the user canceled the job | `job`, `exec` |

The `status` metric has one of these values:
- `0`: submitted
- `1`: initialization phase
- `2`: running
- `3`: suspended
- `4`: exporting snapshot
- `5`: completing phase
- `6`: failed
- `7`: completed successfully

The `userCancelled` metric is `1` if the user canceled the job. It is `0` if the job is running, completed successfully, or failed because of an error other than cancellation by the user. This metric is available only through the [Job API](../operate-and-manage/maintaining-a-cluster/monitoring.mdx#via-job-api).

Each member reports one value for each metric for each vertex:

| Name | Description | Tags |
| --- | --- | --- |
| `snapshotBytes` | Total number of bytes written out in the last snapshot | `job`, `exec`, `vertex` |
| `snapshotKeys` | Total number of keys written out in the last snapshot | `job`, `exec`, `vertex` |

Each member reports one value for each metric for each ordinal of each vertex of each job execution. The metrics are present only for distributed edges, which are edges that produce network traffic:

| Name | Description | Tags |
| --- | --- | --- |
| `distributedBytesIn` | Total number of bytes received from remote members | `job`, `exec`, `vertex`, `ordinal` |
| `distributedBytesOut` | Total number of bytes sent to remote members | `job`, `exec`, `vertex`, `ordinal` |
| `distributedItemsIn` | Total number of items received from remote members | `job`, `exec`, `vertex`, `ordinal` |
| `distributedItemsOut` | Total number of items sent to remote members | `job`, `exec`, `vertex`, `ordinal` |

A processor is the parallel worker that does the work of a vertex, and the `proc` tag holds the global index of the processor instance. Each member reports one value for each metric for each processor instance:

| Name | Description | Tags |
| --- | --- | --- |
| `topObservedWm` | Highest `coalescedWm` value on any input edge of the processor | `job`, `exec`, `vertex`, `proc` |
| `coalescedWm` | Highest watermark received from all inputs that was sent to the processor to handle | `job`, `exec`, `vertex`, `proc` |
| `lastForwardedWm` | Last watermark emitted by the processor to output | `job`, `exec`, `vertex`, `proc` |
| `lastForwardedWmLatency` | Difference between `lastForwardedWm` and the system time when the metrics were collected | `job`, `exec`, `vertex`, `proc` |
| `queuesCapacity` | Total capacity of the input queues | `job`, `exec`, `vertex`, `proc` |
| `queuesSize` | Total number of items waiting in the input queues | `job`, `exec`, `vertex`, `proc` |

Each member reports one value for each metric for each input or output edge of each processor instance. The `ordinal` tag holds the ordinal of the edge, or `snapshot` for output items written to the state snapshot:

| Name | Description | Tags |
| --- | --- | --- |
| `topObservedWm` | Highest watermark received from any input on the edge | `job`, `exec`, `vertex`, `proc`, `ordinal` |
| `coalescedWm` | Highest watermark received from all upstream processors on the edge | `job`, `exec`, `vertex`, `proc`, `ordinal` |
| `emittedCount` | Number of emitted items including watermarks and snapshot barriers | `job`, `exec`, `vertex`, `proc`, `ordinal` |
| `receivedCount` | Number of received items excluding watermarks and snapshot barriers | `job`, `exec`, `vertex`, `proc`, `ordinal` |
| `receivedBatches` | Number of received batches | `job`, `exec`, `vertex`, `proc`, `ordinal` |

Unlike `distributedItemsOut`, `emittedCount` includes items emitted to local processors. The `receivedCount` value is the number of items that the `Processor.process` method receives. The `Processor.process` method receives items in batches, and `receivedBatches` counts those batches. To get the average batch size, divide `receivedCount` by `receivedBatches`. Under low load, the average batch size is 1.

Only some types of processor report these metrics, and the `procType` tag identifies the type of processor. Each member reports one value for each metric for each processor instance:

| Name | Description | Tags |
| --- | --- | --- |
| `numInFlightOps` | Number of pending, in-flight operations in asynchronous mapping processors. See <Variable href="https://docs.hazelcast.org/docs/{os-version}/javadoc/com/hazelcast/jet/core/processor/Processors.html#mapUsingServiceAsyncP-com.hazelcast.jet.pipeline.ServiceFactory-int-boolean-com.hazelcast.function.FunctionEx-com.hazelcast.function.BiFunctionEx-" text="Processors.mapUsingServiceAsyncP" code />. | `job`, `exec`, `vertex`, `proc`, `procType` |
| `totalKeys` | Number of active keys tracked by a session window processor. | `job`, `exec`, `vertex`, `proc`, `procType` |
| `totalWindows` | Number of active windows tracked by a session window processor. See <Variable href="https://docs.hazelcast.org/docs/{os-version}/javadoc/com/hazelcast/jet/core/processor/Processors.html#aggregateToSessionWindowP-long-long-java.util.List-java.util.List-com.hazelcast.jet.aggregate.AggregateOperation-com.hazelcast.jet.core.function.KeyedWindowResultFunction-" text="Processors.aggregateToSessionWindowP" code />. | `job`, `exec`, `vertex`, `proc`, `procType` |
| `totalFrames` | Number of active frames tracked by a sliding window processor. | `job`, `exec`, `vertex`, `proc`, `procType` |
| `totalKeysInFrames` | Number of grouping keys associated with the active frames of a sliding window processor. See <Variable href="https://docs.hazelcast.org/docs/{os-version}/javadoc/com/hazelcast/jet/core/processor/Processors.html#aggregateToSlidingWindowP-java.util.List-java.util.List-com.hazelcast.jet.core.TimestampKind-com.hazelcast.jet.core.SlidingWindowPolicy-long-com.hazelcast.jet.aggregate.AggregateOperation-com.hazelcast.jet.core.function.KeyedWindowResultFunction-" text="Processors.aggregateToSlidingWindowP" code />. | `job`, `exec`, `vertex`, `proc`, `procType` |
| `lateEventsDropped` | Number of late events dropped by processors because the watermark has already passed their windows. | `job`, `exec`, `vertex`, `proc`, `procType` |

## Map

The Reset column shows the reset behavior of the metrics. There are two types of reset: one occurs on a node restart (indicated by `N`), and the other on a cluster restart (indicated by `C`). For example, metrics relating to map operations such as get, put, and remove track operations executed by a member during its runtime, and these are reset upon a node restart. Metrics such as hits, evictions, and expirations are tracked at the cluster level, and these are retained when a member is restarted.

The following metrics describe a map on the member:

| Name | Unit | Description | Reset |
| --- | --- | --- | --- |
| `map.backupCount` | count | Number of backups per entry | C |
| `map.backupEntryCount` | count | Number of backup entries held by the member | C |
| `map.backupEntryMemoryCost` | bytes | Memory cost of backup entries in this member | C |
| `map.creationTime` | ms | Creation time of the map on the member | N |
| `map.dirtyEntryCount` | count | Number of dirty entries that the member owns, which are entries that are updated but not yet persisted | N |
| `map.entrySetCount` | count | Number of entry set operations on this member | N |
| `map.evictionCount` | count | Number of evictions of locally owned entries, excluding backups | C |
| `map.expirationCount` | count | Number of expirations of locally owned entries, excluding backups | C |
| `map.getCount` | count | Number of local get operations on the map, including gets for entries that do not exist | N |
| `map.heapCost` | count | Total heap cost for the map on this member | C |
| `map.hits` | count | Number of reads of existing, locally owned entries by any type of operation, such as get, set, or put | C |
| `map.indexedQueryCount` | count | Total number of indexed local queries performed on the map | N |
| `map.indexesSkippedQueryCount` | count | Total number of local queries performed on the map which cannot use indexes | N |
| `map.noMatchingIndexQueryCount` | count | Total number of local queries performed on the map which had no matching index | N |
| `map.lastAccessTime` | ms | Last access (read) time of the locally owned entries | C |
| `map.lastUpdateTime` | ms | Last update time of the locally owned entries | C |
| `map.lockedEntryCount` | count | Number of locked entries that the member owns | C |
| `map.merkleTreesCost` | count | Total heap cost of the Merkle trees used | N |
| `map.numberOfEvents` | count | Number of local events received on the map | N |
| `map.numberOfOtherOperations` | count | Total number of other operations performed on this member | N |
| `map.ownedEntryCount` | count | Number of map entries owned by the member | C |
| `map.ownedEntryMemoryCost` | bytes | Memory cost of owned map entries on this member | C |
| `map.putCount` | count | Number of local put operations on the map | N |
| `map.queryCount` | count | Number of queries executed on the map | N |
| `map.queryLimiterHitCount` | count | Number of times the query result size limiter was hit on this member | N |
| `map.removeCount` | count | Number of local remove operations on the map | N |
| `map.setCount` | count | Number of local set operations on the map | N |
| `map.totalGetLatency` | ms | Total latency of local get operations on the map | N |
| `map.totalMaxGetLatency` | ms | Maximum latency of local get operations on the map | N |
| `map.totalMaxPutLatency` | ms | Maximum latency of local put operations on the map | N |
| `map.totalMaxRemoveLatency` | ms | Maximum latency of local remove operations on the map | N |
| `map.totalMaxSetLatency` | ms | Maximum latency of local set operations on the map | N |
| `map.totalPutLatency` | ms | Total latency of local put operations on the map | N |
| `map.totalRemoveLatency` | ms | Total latency of local remove operations on the map | N |
| `map.totalSetLatency` | ms | Total latency of local set operations on the map | N |
| `map.valuesCount` | count | Number of values operations on this member | N |
| `map.store.offloaded.operations.waitingToBeProcessedCount` | count | Number of offloaded map store operations waiting to be processed | N |

The `map.queryCount` value can be imprecise for queries that use partition predicates (`PartitionPredicate`) on off-heap storage.

The following metrics describe an index of a map on the member:

| Name | Unit | Description | Reset |
| --- | --- | --- | --- |
| `map.index.averageHitLatency` | ns | Average hit latency for the index on this member | N |
| `map.index.averageHitSelectivity` | percent | Average selectivity of the hits served by the index on this member, from 0.0 to 1.0 | N |
| `map.index.creationTime` | ms | Creation time of the index on this member | N |
| `map.index.hitCount` | count | Total number of index hits | N |
| `map.index.insertCount` | count | Number of insert operations performed on the index | N |
| `map.index.memoryCost` | bytes | Local memory cost of the index | N |
| `map.index.queryCount` | count | Total number of queries served by the index | N |
| `map.index.removeCount` | count | Number of remove operations performed on the index | N |
| `map.index.totalInsertLatency` | ns | Total latency of insert operations performed on the index | N |
| `map.index.totalRemoveLatency` | ns | Total latency of remove operations performed on the index | N |
| `map.index.totalUpdateLatency` | ns | Total latency of update operations performed on the index | N |
| `map.index.updateCount` | count | Number of update operations performed on the index | N |
| `map.index.partitionsIndexed` | count | Number of partitions the index is built for on the local member | N |
| `map.index.partitionUpdatesStarted` | count | Number of times a partition set change started for the index | N |
| `map.index.partitionUpdatesFinished` | count | Number of times a partition set change completed for the index | N |
| `map.index.notReadyQueryCount` | count | Number of queries which matched the index during a partition set change | N |

A `map.index.averageHitSelectivity` value close to 1.0 means high selectivity, and the index is efficient. A value close to 0.0 means low selectivity, and the index is little more efficient than a full scan.

The `map.index.hitCount` value can be greater than `map.index.queryCount`, because a single query can hit the same index more than once.

For on-heap indexes in `OBJECT` or `BINARY` format, the `map.index.memoryCost` value is a best-effort approximation, not the exact on-heap memory usage of the index.

The `map.total*Latency` and `map.totalMax*Latency` metrics are measured only on members, and do not represent the overall performance of the cluster. To get the average latency of an operation, divide its total latency by its count. For example, divide `map.totalGetLatency` by `map.getCount`.

A client `putAll` call can increase `vectorCollection.putAllCount` more than once, because the client splits the entries by partition. The client sends a partition's entry as a `set` operation when the partition has only one entry, which increases `vectorCollection.setCount` instead of `vectorCollection.putAllEntryCount`.

The `vectorCollection.searchIndexQueryCount` value includes search retries, for example retries caused by concurrent modifications. Without retries, it equals `vectorCollection.searchCount` multiplied by the number of non-empty partitions. With retries, it is larger.

The vector collection latency metrics are measured only on members, and do not represent the overall performance of the cluster. To get the average latency of an operation, divide its total latency by its count. For example, divide `vectorCollection.totalGetLatency` by `vectorCollection.getCount`.
